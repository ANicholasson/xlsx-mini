# Governance and release through rulesets, changesets and trusted publishing

`main` is protected by a ruleset that requires pull requests, the CI checks, squash merges with a conventional-commit title, linear history and no force pushes, applied to administrators too. Releases flow through changesets: a Version Packages pull request on `main`, and merging it publishes to npm through trusted publishing with provenance, so no long-lived token exists anywhere. Actions are pinned to commit SHAs, workflow permissions default to read, Dependabot updates grouped weekly, CodeQL scans. Community files stay minimal on purpose: a short contributing guide (issue first for features, straight pull request with a failing test for fixes), a short security policy using GitHub private reporting, one bug-report form, one pull-request template. `CODING_STANDARDS.md` holds only judgement calls; mechanical rules live in tooling.

In practice: the required checks are the lint, typecheck, build and validate jobs, the four test jobs (Node 20, 22 and 24 on Ubuntu, Node 24 on Windows) and the title check; CodeQL and the benchmark report inform. The validate job installs LibreOffice Calc and compares every golden fixture, converted to CSV, with the committed CSV cell for cell. The release workflow publishes through npm trusted publishing, so no npm token exists; the one token nuance is the version pull request, which gets no checks when the workflow's own token opens it, so a fine-grained token scoped to this repository may be stored as `CHANGESETS_TOKEN` for that single purpose, or the pull request is closed and reopened by hand.
