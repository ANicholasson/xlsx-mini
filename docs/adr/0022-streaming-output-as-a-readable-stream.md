# Streaming output as a second entry point returning a ReadableStream

`writeXlsx` keeps returning one `Uint8Array`, byte for byte as before and on the same code path. Next to it, `streamXlsx(workbook, options)` returns a web `ReadableStream<Uint8Array>` that produces the package as it is pulled: a `Response` body on any server runtime, `pipeTo` a file's `WritableStream`, `Readable.fromWeb` for a Node stream, or `for await` over the chunks. Peak memory does not grow with the row count; it grows only with distinct styles, which are bounded by the caller's vocabulary rather than the data. Rows may come from an `AsyncIterable`, so a database cursor can feed a sheet page by page.

## Why a second entry point

A sink option on `writeXlsx` would give one function two return types and put a branch on the byte path. A `ReadableStream` is the one return type every target accepts without conversion, carries backpressure, and is pull-based. The stream is created with a high-water mark of zero, so nothing is rendered and no row source is read until the consumer reads; with the default mark the runtime pulls once on creation. `streamXlsx` validates the workbook synchronously and throws before the stream exists; a bad cell met while rendering errors the stream, which is the most a half-sent response can do. Cancelling the stream returns the row iterator, aborts the compressor and drops the string table, so a cursor behind an abandoned response is closed. `writeXlsx` keeps synchronous rows; given an `AsyncIterable` it throws a coded error, since a caller who holds the whole result in memory anyway can read `new Response(streamXlsx(workbook)).arrayBuffer()`.

## What streaming changes in the package

- **Inline strings by default.** A shared-strings table must be held until the last sheet is rendered and grows with every distinct string, so a million-row export of mostly distinct text would hold most of the file in memory. Streamed sheets write text as `t="inlineStr"` cells with the same escaping and `xml:space` handling as the table's items. The cost is one escape per text cell instead of one per distinct string, which the streamed benchmark variant measures. `strings: "shared"` keeps the table for callers who want the smaller file and can afford the memory, and is what the part-for-part comparison with the byte path uses; the byte path keeps shared strings and is unchanged. In inline mode the shared-strings part is still written, empty, so the content types and relationships are the same in both modes.
- **Data descriptors, never with STORE.** A streamed entry's local header sets flag bit 3 and leaves CRC and sizes at zero; they follow the data in a descriptor with its signature and are repeated in the central directory, where every reader this project targets finds them. A STORE entry has no end marker, so a sequential reader cannot find its descriptor: Java's `ZipInputStream` rejects the combination outright and commons-compress, which Apache POI uses when given a stream, refuses it by default. Where the runtime has no raw deflate, a streamed entry is therefore still method 8, built from stored deflate blocks: a five-byte header per block of up to 65 535 bytes, plain JavaScript, deterministic, and valid for every inflater. The byte path keeps its layout, sizes in the local header and no descriptors, so its bytes are identical to 0.2.0.
- **Part order.** The workbook part names each autofilter range and the styles and shared-strings parts are complete only after the last sheet, so a streamed package writes `[Content_Types].xml`, the two relationship parts, the sheets, then `xl/workbook.xml`, `xl/styles.xml` and `xl/sharedStrings.xml`. Readers locate parts through the central directory, so order carries no meaning; the byte path keeps its order. A part's local header is written before its first row, so the first bytes leave early.
- **No `dimension` element when streaming.** The used range is known only after the last row. The byte path keeps writing it: openpyxl's read-only mode reports a sheet without it as unsized, and the golden fixtures stay as they are. The worksheet head is rendered by one function from an optional range and written after the rows on the byte path, as today, and before the first row when streaming; the comparison test strips that one element.
- **Limits.** Every entry's sizes, every offset and the entry count are checked against the 32-bit and 16-bit fields; a package that would pass them errors the stream with `PACKAGE_TOO_LARGE`, as the byte path throws. Zip64 is not written.

## How the row loop stays one loop

The worksheet renderer becomes an object that takes one row at a time and emits encoded chunks of at most 65 535 bytes, so each chunk is one stored deflate block where that fallback applies: the byte path feeds it the rows in a plain loop and collects the chunks, which is what the byte sink already did internally; when streaming, each part is a `ReadableStream` whose pull feeds rows until a chunk is ready, awaiting the source only when the rows are an `AsyncIterable`, piped through the runtime's `CompressionStream`, which supplies backpressure and abort. Feeding a compressor by hand inside a pull stalls on every runtime once its output queue fills. CRC-32 runs as state on the uncompressed chunks as they pass. The outer stream's pull loops until it has enqueued something, since a pull that enqueues nothing is not called again. One call per row and per chunk is the whole overhead; per-cell work is untouched, and the byte path is measured against the noise band on the pull request.

## What the change must also carry

The memory benchmark gains a streamed wide-table measurement at 100 000 and 1 000 000 rows into a null sink, with its number in ADR 0021. The runtime matrix streams the scenario workbook on every host. A README snippet streams a `Response` body from a route handler and is run by the tests. Streamed fixtures, deflate and stored-block, open clean in the four applications and are recorded in the compatibility log. A minor changeset.

## Considered and rejected

- A sink option on `writeXlsx`: two return types behind one name, and a branch on the byte path.
- An async iterable instead of a `ReadableStream`: a `ReadableStream` is already async-iterable on all five runtimes and a `Response` takes it as it is; the reverse needs an adapter.
- Shared strings by default when streaming: flat memory is the point of streaming, and the option remains.
- Buffering each part and writing sizes up front, so the byte layout could serve both paths: one compressed sheet in memory is not flat memory.
- Dropping `dimension` from the byte path too, for one renderer and a cleaner comparison: a regression for readers that rely on it, and every golden fixture would change for no gain to byte-path users.
- STORE entries with descriptors where deflate is unavailable: valid zip, unreadable by sequential readers on the JVM.
